## Framework relationship and the boundary of the Tavi PoC

The **XBRL GL Next Requirements Specification** (Section 4 and GL-REQ-0301–0303) defines the common semantic/logical approach and the supported XBRL 2.1 and OIM bindings. The **Taxonomy Framework** documents allocate the responsibilities as follows:

| Document | Relationship to this guide |
| --- | --- |
| Requirements Specification, §§4 and 6.6 | Common semantic pipeline, binding-specific realisation and cross-binding objectives; it does **not**, by itself, define this Tavi JSON generator as a normative binding. |
| Part 1: General rules, §§5.2–5.3, 5.4, 5.5–5.6, 8.5 and 11 | FSM → BSM → LHM candidate → LHM reviewed → formal HMD; module ownership, palette assembly, QName, Semantic Path and syntax-binding boundary. The generator consumes the **formal 18-column HMD for taxonomy**, not a raw FSM, BSM, or reviewed LHM. |
| Part 2: Tuple palette taxonomy | XBRL 2.1 Tuple realisation from the formal HMD. **Not generated by this script.** |
| Part 3: OIM palette taxonomy, especially §§5–8 | Conventional OIM concept/dimensional realisation and separation of taxonomy from xBRL-CSV report metadata/data. It is useful architectural context, **not a claim that the Tavi JSON output is the Part 3 normative package**. |
| Part 4: Aligned Pool and extension governance | COR and BTX as Shared semantic models; COR-JPN as an Aligned extension specialising classes of Shared COR, and BTX-PINT as an Aligned extension specialising classes of Shared BTX, under Part 4 governance. Specialisation → Graph Walk → reviewed LHM → Post-Graph Walk precedes Tavi generation; no implicit mappings are added by the generator. |

**Formal input boundary.** Part 1 §5.3.9 specifies the 18-column HMD for taxonomy and column 9 `value_domain`. It preserves reviewed row order and semantic/provenance fields. Part 1 §5.3.11 separates semantic `datatype` from the binding to a physical item type and from a governed Value Domain. The PoC generator implements only the **explicit 15-type in-code mapping** documented below; its successful Arelle validation must **not** be represented as evidence that every Part 1 Value Domain, extensible-enumeration, packaging, or cross-binding conformance requirement has been implemented. No Value Domain definitions, external datatype mapping files or overlays are read by this script.

**Palette model.** The formal HMD selects a root-specific set of concepts from module-owned semantics; Tavi is evaluated here as an additional JSON taxonomy representation of that selected HMD. The four cases are independent palettes/assemblies; shared names or identical semantic paths across models are not a prerequisite. The actual Tavi mapping described in the next section is **existing PoC behaviour**, not a new normative rule added to Parts 1–4.

## Shared semantic models and Aligned extensions; Specialisation and Graph Walk

**Part 4 classification for the four models in this PoC:**

| Model | Semantic classification | Relation |
| --- | --- | --- |
| COR | **Shared** | Shared foundational accounting-entry semantics. |
| BTX | **Shared** | Shared foundational business-transaction semantics. |
| COR-JPN | **Aligned extension** | **Specialises and extends classes defined in Shared COR** for the Japan-aligned model. |
| BTX-PINT | **Aligned extension** | **Specialises and extends classes defined in Shared BTX** for the PINT-aligned model. |

COR-JPN extends **COR classes through Specialisation**; BTX-PINT extends **BTX classes through Specialisation**. These are explicit class-level specialisation relationships, not merely independent models that happen to use related semantics. The Aligned extensions also maintain correspondence with their respective external source definitions, with source mapping and governance upstream under the **Aligned Pool** (Part 4). They do not redefine COR or BTX as Aligned, and they are **not** Tavi-specific extensions. The models each have their own effective root, reviewed hierarchy, HMD and generated Tavi taxonomy; the extension relationship does not require identical QNames, semantic paths or concept sets across their independently generated outputs.

**Semantic processing before Tavi generation** follows the Framework's established sequence:

```text
Shared FSM classes: COR               Shared FSM classes: BTX
  + COR-JPN Aligned definitions          + BTX-PINT Aligned definitions
    -> Specialisation of COR classes       -> Specialisation of BTX classes
         (COR-JPN BSM)                        (BTX-PINT BSM)

  Each applicable BSM then proceeds independently:
    -> Graph Walk (candidate LHM)
    -> model definer's review (LHM reviewed)
    -> Post-Graph Walk (formal 18-column HMD_for_taxonomy, per effective root)
    -> hmd_to_tavi.py (Tavi taxonomy JSON, one selected HMD per invocation)
```

- **Specialisation** derives the applicable Aligned class specialisations from their Shared parent classes: COR → COR-JPN and BTX → BTX-PINT. It is a class-level extension, not a claim that the generated Tavi taxonomies must share identical concept lists, QNames or paths. It applies accepted extension definitions to the applicable foundational semantics; the corresponding source classifications, identifiers, module ownership, source mappings and review decisions are governed upstream. It is not performed by the Tavi generator.
- **Graph Walk** derives the candidate logical hierarchy from the specialised model. That candidate is **not** the authoritative taxonomy input; the model definer reviews it and approves `LHM reviewed`. For the Candidate LHM at this stage, column nine is `association_role`; distinguish this from the formal 18-column HMD's `value_domain` field. Confirm the Reviewed LHM column contract against the applicable current authority rather than assuming the Candidate field name.
- **Post-Graph Walk** starts from approved `LHM reviewed`, identifies effective level-1 roots, excludes `0..0` subtrees, regenerates reviewed-QName-based XPath values and produces the independently validated formal HMD for each root. The formal HMD's ninth column is `value_domain`.
- **Tavi generation** begins *after* this pipeline. The script consumes a completed 18-column HMD and does not read the FSM, Aligned registry, BSM, candidate LHM, reviewed LHM, or View definition at runtime. Its four-model acceptance verifies the **HMD-to-Tavi** boundary, **not** that third parties can reproduce the entire FSM-extension-to-HMD pipeline from today's public clone.

**Part 4 classification versus HMD assembly.** COR and BTX are **Shared** semantic models. COR-JPN **specialises classes from COR** and BTX-PINT **specialises classes from BTX** as **Aligned extensions**; this is a semantic-model relationship, not an assertion that the Tavi JSON generator performs the extension. The informative `businessTransactions` assembly example in Part 4 illustrates an independent root-specific HMD alongside `accountingEntries`; HMD assembly and Aligned semantic extension are different concerns. For Tavi, each of the four accepted HMDs is generated as a distinct taxonomy.

**Reproduction boundary:** the commands in this README reproduce Tavi JSON **from existing accepted HMDs**. Reproducing Specialisation, Graph Walk or Post-Graph Walk themselves would require their own authoritative FSM/extension source versions, mappings, reviewed LHM and execution evidence. Those upstream steps are described for traceability, not added as unexecuted mandatory commands or extra acceptance tests in this taxonomy-only PoC.

## Generator contract: what `hmd_to_tavi.py` does

**Program and invocation.** `tavi-poc/tools/hmd_to_tavi.py` is a Python 3.10+ standard-library CLI, reading one HMD CSV and writing one Tavi taxonomy JSON. Its recorded arguments are:

| Option | Contract |
| --- | --- |
| `--hmd PATH` | Required input: UTF-8/UTF-8-BOM CSV, precisely the accepted 18 headers in order; 18-column `value_domain` formal HMD. |
| `--output PATH` | Required new JSON destination. The script rejects an existing output and rejects an output path identical to the input. |
| `--version TEXT` | Required taxonomy version string; the accepted four-model examples use `2026-10-26-candidate`. |
| `--include-documentation` | Emit available HMD English/Japanese definitions as `xbrl:documentation` labels, without filling in missing translations. Enabled in all recorded four-model executions. |
| `--documentation-target QName` | Existing optional scoped documentation selection; not used in the recorded four-model commands. |

**HMD schema.** The ordered headers are:

```text
sequence,module,level,type,identifier,name,datatype,multiplicity,value_domain,definition,label_local,definition_local,source_bsm_id,semantic_path,associated_module,class_term,local_name,xpath
```

**Existing mapping implemented in the accepted generator:**

- A single root Class (`C`) is identified from the HMD. Root QName is derived from its module and `local_name`; it is not hard-coded to COR. A Class becomes a `p_` anchor concept, and an Attribute (`A`) becomes a concept with its explicit module/local identity and a distinct datatype declaration. Reference/Association (`R`) rows do not become concept objects; their attributes are associated with the nearest enclosing Class under the existing path-based treatment.
- Hierarchy relationships are generated from parent/child Class ownership and HMD row order. Each Class has a cube; attribute membership contributes concept domains, and repeating Classes contribute typed occurrence dimensions along ancestor scopes. Generated networks are root-specific. The code preserves the existing treatment of `multiplicity` and `semantic_path`, rather than inferring a new hierarchy from labels or names.
- The generator uses module namespaces of the form `https://www.xbrl.or.jp/taxonomy/xbrl-gl-next/{module}` with the recorded standard `xbrl`, `xbrli` and `xs` aliases, and writes standard English/Japanese labels where the source values exist. `--include-documentation` adds only source definitions available in those languages.
- JSON output uses `json.dumps(ensure_ascii=False, indent=2)` plus a final newline; text-mode writing does not force LF across operating systems. It has no runtime dependency on a reference taxonomy JSON, HMD manifest, external datatype-binding CSV, or View definition.
- It rejects malformed/empty HMD, unknown row types, duplicate semantic paths or concept identities, invalid module/local name, unsupported datatype/multiplicity, and invalid or multiple roots. It does not modify the input HMD.

**Explicit semantic-term-to-Tavi-baseType mapping in this PoC (15 values):**

| HMD datatype | Tavi `baseType` | HMD datatype | Tavi `baseType` |
| --- | --- | --- | --- |
| String | `xs:string` | Token | `xs:token` |
| Date Time | `xs:dateTime` | Boolean | `xs:boolean` |
| Monetary | `xbrli:monetary` | Decimal | `xs:decimal` |
| QName | `xs:QName` | Pure | `xbrli:pureType` |
| Date | `xs:date` | Integer | `xs:integer` |
| anyURI | `xs:anyURI` | Identifier | `xs:string` |
| Code | `xs:token` | Text | `xs:string` |
| Amount | `xbrli:monetary` | — | — |

The four additions `Identifier`, `Code`, `Text` and `Amount` were needed by BTX-PINT. These values describe **the accepted PoC script**, not an instruction to alter the source HMD or change the Framework's authoritative mapping contract.

**Workflow for a consumer:** obtain the correct HMD edition and generator with the listed SHA-256 identities; start in the clone root; run exactly one of the model-specific examples below with a **new** output path and the recorded options; check the output against the corresponding reference JSON using the approved newline-only content comparison; then validate the generated JSON in the specified patched Arelle source environment. The historical successful commands and the path-adapted examples have different provenance and are labelled accordingly.
